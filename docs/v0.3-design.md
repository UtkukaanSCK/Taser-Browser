# Taser v0.3: extensions research and design

Base: `ce8fd15` (v0.2 final). The release binary is 1,260,032 B.
WebView2 Runtime: **157.0.4341.46** (`BrowserVersionString`). wry 0.57.2, webview2-com 0.39.1, windows 0.62.2.

The request: no password manager. uBlock Origin comes preinstalled for ad blocking. The Chrome Web Store (CWS) extension page works in the browser, and extensions can be installed straight from it.

Short answers:
- **WebView2 157 runs Chrome extensions, MV2 and MV3, and they block ads.** wry already exposes the switch, so no fork is needed.
- **Preinstall uBlock Origin Lite (MV3), not uBlock Origin (MV2).** The CWS no longer serves uBO.
- **Isolation is a hard requirement.** An extension in the same profile as the UI webview can call the UI's IPC. The UI and the overlay move to their own WebView2 profile.
- **The CWS page works.** Its "Add to Chrome" button drives WebView2's own Edge-branded install dialog. Taser intercepts that call and runs its own install flow instead.

## Part A: answers

### 1. WebView2 extension APIs, and how to turn them on through wry

**APIs in webview2-com-sys 0.39.1**
- `ICoreWebView2EnvironmentOptions6`: `Set/AreBrowserExtensionsEnabled`. It is an environment option, so it is fixed when the environment is created.
- `ICoreWebView2Profile7`: `AddBrowserExtension(folder, handler)` and `GetBrowserExtensions(handler)`.
- `ICoreWebView2BrowserExtension`: `Id`, `Name`, `IsEnabled`, `Enable(bool, handler)` and `Remove(handler)`.
- There is **no** API to open an extension's action popup or options page, to get its icon or version, or to update it.

**wry 0.57.2 already wires the option. No fork is needed.**
- `WebViewBuilderExtWindows::with_browser_extensions_enabled(true)` sets the option in `create_environment`.
- Taser creates the environment in `ui::build`, via `with_additional_browser_args`. Every other webview reuses it through `with_environment`. **That one builder is the only place to add the call.**
- Do not use wry's `with_extensions_path`. It calls `AddBrowserExtension` for every subfolder each time *any* webview is built (every tab), and it ignores the result.
- `with_profile_name` (`ControllerOptions.ProfileName`) is the profile switch section 8 needs.

**Extensions persist in the profile.**
- r3 reopened r2's user-data folder and added nothing. uBOL and the probe extension were still listed, enabled, and blocking.
- WebView2 remembers the folder path. Taser only calls `AddBrowserExtension` to install, not on every start.

**Two built-in extensions are always listed** in every profile:
- "Microsoft Clipboard Extension" `dgiklkfkllikcanfonkcabmbdfmgleag`
- "Microsoft Edge PDF Viewer" `mhjfbmdgcfjbbpaeojofohoefgiehjai`

The management UI must hide them.

**Timing:** `AddBrowserExtension` took 188 ms for uBO (r1), and 537 ms for uBOL plus the probe added together (r2).

### 2. uBlock Origin (MV2) and uBlock Origin Lite (MV3) in WebView2 157

**uBO 1.76.4 (MV2), from the GitHub `.chromium.zip`, r1**
- Loads: `AddBrowserExtension` hr=Ok, enabled=true.
- Blocks: neither `xbt=1` nor `xbt=2` reached the server, and both controls did. The page still saw `load`/`ok`, because uBO answers those two with its own neutered stand-ins.
- Its popup counted "Blocked since install 3 (23%)".

**uBOL 2026.1116.1650 (MV3), from the CWS CRX with `"key"` inserted, r2**
- Loads with the **store id** `ddkjiahejlhfcafbddmgiahcphecmpfh`.
- Blocks: no `xbt=1` or `xbt=2` request reached the server, and the controls did.
- After a restart with nothing re-added (r3), it still blocks.
- It needs `declarativeNetRequest`, `offscreen`, `userScripts` and `scripting`. It loaded and worked with them. Its dashboard renders ("Settings Filter lists Custom filters About", default filtering mode).

**Writes into its own folder.** WebView2 wrote 13.9 MB of indexed DNR rulesets into the uBOL folder (`_metadata\generated_indexed_rulesets`), next to its 33 MB of files.
- The install folder must stay writable.
- Allow about 47 MB on disk for uBOL.

**Cosmetic filtering** is not proven on the local test page: the test `div`s stayed `display:block` with both extensions. uBO did hide `#ad_banner` on the same-profile UI look-alike page in r1, so cosmetic filtering runs. **Not verified:** cosmetic filtering on a real ad-carrying site.

**Availability**
- The CWS no longer serves uBO MV2 (`cjpalhdlnbpafiamejdnhcphjbkeiagm`). The download endpoint answers 204 for prodversion 130, 137, 138 and 157, and updatecheck answers `noupdate`.
- uBOL is served.
- `chrome.webstorePrivate.getMV2DeprecationStatus` exists in this runtime. **MV2 support can be withdrawn from WebView2 the way it was from Chrome.**

### 3. Extension popup and options pages

**Opening them works.** Navigating a content-profile webview to `chrome-extension://<id>/<page>` works:
- uBO `popup-fenix.html` and `dashboard.html`, plus the probe's `popup.html` and `options.html`, in r1
- uBOL `popup.html` and `dashboard.html`, in r2

They load, render and talk to their service worker (`runtime.sendMessage` replied).

**The catch: which tab is "current".** Each WebView2 webview is a separate tab in a separate window (`windows.getAll` says type `popup`), so a popup page in its own webview is "the active tab of the current window".
- uBOL's popup does `tabs.query({active:true, currentWindow:true})` and showed "not a website" (r2, `D-0-popup.html.png`).
- uBO's popup accepts `?tabId=` (`popup-fenix.js:1459`), but uBOL's does not.

**Fix, verified in r3.** An initialization script on the popup webview, which runs only on `chrome-extension:`, rewrites `tabs.query({active, currentWindow})` to return the content tab that Taser has active, matched by URL.
- Result: uBOL's popup then showed "127.0.0.1 / filtering mode optimal / Remove an element / Create a custom filter" for the content page (`$S\runs\r3\D-0-popup.html.png`).

**Other APIs, as seen by the service worker:** `action` (with `openPopup`), `management`, `permissions`, `runtime`, `scripting`, `storage`, `tabs`, `webNavigation` and `windows`.
- `chrome.tabs.create` arrives as `NewWindowRequested` with `IsUserInitiated=true` on a content webview (r1–r3). It follows Taser's normal new-window path and opens a tab.
- **Not verified:** what `action.openPopup` does here.

### 4. The Chrome Web Store page

**How the store sees Taser**
- `https://chromewebstore.google.com/detail/<slug>/<id>` renders fully.
- The user agent is `Chrome/157.0.0.0` with no `Edg`.
- `chrome.webstorePrivate` is present, an Edge build of it (`EdgeAccountType`, `getMV2DeprecationStatus`, `beginInstallWithManifest3`, …).
- The store reads the profile's extension list. With uBOL loaded under its store id, the uBOL page showed **"Remove from Chrome"** (r2).

**What the store's buttons do (r2–r4)**
- **"Add to Chrome"** (Dark Reader, not installed) puts the button into a spinner. WebView2 then opens its own top-level window, `Chrome_WidgetWin_1` in `msedgewebview2.exe`, titled *Add "Dark Reader" to Microsoft Edge?*, listing the permissions with "Add extension / Cancel" (`$S\runs\r4\win-6s.png`).
- **"Remove from Chrome"** opens *Remove "uBlock Origin Lite" from Microsoft Edge?* (`$S\runs\r2\win-after-click.png`).

**Not verified: what happens after accepting the native dialog.** Accepting it needs a click on a desktop window, which the spike's rules forbid. The native path is not documented for WebView2, and it is branded "Microsoft Edge". Taser therefore does not rely on it.

**The store's install call can be intercepted (r6).**
- An initialization script on the store origin wraps `chrome.webstorePrivate.beginInstallWithManifest3`.
- The click then calls the wrapper with `{id, manifest, iconUrl, localizedName, …}`, the full manifest included. No native dialog opens.
- Returning `'user_cancelled'` leaves the page usable.

Hiding `chrome.webstorePrivate` altogether is worse (r5): the page shows "Item currently unavailable" and greys out the button.

**"Remove from Chrome" uses a public API (r7).**
- With every `webstorePrivate` and `management` function wrapped and logged, "Remove from Chrome" called `chrome.management.uninstall("ddkj…", {showConfirmDialog: true}, cb)`. With that wrapped, no native window opened.
- To decide which button to show, the page calls `management.getAll` and `webstorePrivate.getExtensionStatus(id, manifest)`. Taser leaves those alone, so the page keeps showing the true state.

**Decision: own button plus intercepted store button.** Taser detects the detail URL (section B.4) and shows its own **"Ekle"** button, or "Kaldır" when the item is installed. It also routes the store's own button into the same flow.

### 5. CRX download, format, verification, unpacking and HTTP

**Download**
- `https://clients2.google.com/service/update2/crx?response=redirect&prodversion=157.0.4341.46&acceptformat=crx3&x=id%3D<id>%26uc` answers 302 to `clients2.googleusercontent.com/crx/blobs/…`.
- An updatecheck variant (`response=updatecheck`, `x=id%3D<id>%26v%3D<ver>%26uc`) returns gupdate XML with `codebase`, `version`, `size`, `hash_sha256`, or `status="noupdate"`.
- The uBOL CRX (9,097,388 B) matched the `hash_sha256` that updatecheck reported.

**Format.** `Cr24`, version 3, a header length, the protobuf `CrxFileHeader`, then the zip.

**Proofs.** The CWS uBOL file carries 3 proofs, all checked with `openssl`:
- the developer RSA key, whose SHA-256 gives the id `ddkjiahejlhfcafbddmgiahcphecmpfh` = `signed_header_data.crx_id`
- the store's ECDSA publisher key, SHA-256 `61f7f2a6…` = Chromium's `kPublisherKeyHash`
- a second RSA key

**How the extension id is derived.** It is the first 16 bytes of SHA-256(SPKI), written in the letters a–p. An unpacked folder otherwise gets an id from its path (uBO from GitHub got `gmkojlmgklbehlpmonipdjplognmmooa`). Inserting `"key": base64(developer SPKI)` into `manifest.json` keeps the store id. Verified in r2.

**The reader is being built in parallel.** The CRX3 reader and verifier is `src/crx.rs` in the `X-Browser-v03-crx` worktree.
- Verification uses OS CNG and needs no crypto crate.
- Inflate uses `miniz_oxide` 0.9.1.
- It adds **+56,320 B** when wired in.
- This doc does not repeat its format details.

**HTTP: WinHTTP through the `windows` crate** (feature `Win32_Networking_WinHttp`). No reqwest or tokio.
- `$S\whttp` downloaded the uBOL CRX with `WINHTTP_ACCESS_TYPE_AUTOMATIC_PROXY`. It followed the 302 by itself, got status 200 and 9,097,388 B, byte-identical to the earlier download.
- Size: +15,872 B in a stand-alone release binary (121,856 → 137,728 B, the Taser release profile). That is an upper bound inside Taser, which already links most of what that delta contains.
- WebView2 as the downloader is rejected. It has no fetch-to-host API, and driving a hidden webview's download is more code and less control.

**Safe unpacking**
- Reject absolute paths, `..`, drive letters, `:` (alternate data streams), backslashes and reserved device names.
- Reject symlinks: zip entries with a Unix mode `S_IFLNK`.
- Never overwrite outside the target folder.
- Cap entry count, per-file size and total size against the inflated stream, not against the declared sizes.
- Unpack into `<id>\<version>.tmp`, rename into place, then insert `"key"`.

### 6. Updates

WebView2 does not update unpacked extensions, so Taser does.

**Manual first: "Güncellemeleri denetle"** on the Uzantılar page.
1. Send one updatecheck request (multiple `x=` parameters) for every store-installed extension.
2. For each `status="ok"` with a newer `version`, download the `codebase`.
3. Check that `hash_sha256` and `size` match, then verify the CRX (publisher proof plus developer proof, and the id must not change). The developer key must match the installed one.
4. Unpack to `<id>\<new version>\` and insert `"key"`.
5. Call `AddBrowserExtension(new folder)`.
6. Once that succeeds, delete the old folder.

**WebView2's update and remove semantics** (u1–u7, a test MV3 extension with a fixed `"key"`; its service worker logs its version and its `chrome.storage.local`):
- **Update in place.** Calling `AddBrowserExtension` on a new folder for an id that is already installed succeeds and replaces it.
  - u2 and u5: version 2.0 ran with the same id and found version 1.0's storage (`seen: ["1.0"]`).
  - The profile's `Secure Preferences` now point at the new folder. **No `Remove` is needed, and none should be done.**
- **The old folder can go.** u6 deleted the 1.0 folder and added nothing; the extension stayed listed and enabled.
- **`Remove` wipes the extension's storage.** u4a then u4b: removing it and adding it again started with an empty `storage.local`. Updates must never be done as remove plus add, because the user would lose uBOL's settings.
- **A missing folder hides the extension.** u7 started with both folders gone: the extension was no longer listed by `GetBrowserExtensions`, but its entry stayed in the preferences. The start-up reconcile (B.1) repairs this by re-adding or dropping it.

An automatic check (on start, at most once a day, off the UI thread) can come later. It uses the same code.

### 7. Licensing: uBOL is GPLv3, Taser is MIT

**Bundling: Taser conveys uBOL.**
- GPLv3 §5 calls separate, independent programs shipped together an "aggregate". uBOL's licence does not extend to Taser, which stays MIT.
- Taser's distribution must, for uBOL:
  - keep its licence text (`LICENSE.txt` is in the package) and notices
  - provide its Corresponding Source (§6), e.g. §6(d) access to the exact tagged source of the version shipped, kept available for as long as that build is offered. "Source" for uBOL also means its build scripts and filter-list inputs (uBlock filters GPLv3, EasyList/EasyPrivacy GPLv3 or CC BY-SA 3.0, Peter Lowe's list, URLhaus CC0); the uBOL repository carries them.
  - mark it modified (§5(a)) if Taser changes a file. Inserting `"key"` into `manifest.json` counts, so ship the store's files unchanged and insert the key at install time on the user's machine.
- Embedding the package inside `taser.exe` with `include_bytes!` mixes the two into one file. That is defensible as aggregation, but it is a grey zone best avoided.
- Size: +9,097,388 B for the CRX next to a 1.26 MB browser, about 8x.

**Download on first run: Taser conveys nothing of uBOL.**
- The CWS conveys it to the user, as it does for Chrome. There are no GPL obligations on Taser's distribution.
- There is no size impact.
- It comes with the publisher signature checked.

**Recommendation: install on first run from the CWS.**
- It uses the same code path as task 4, with no user action.
- The Uzantılar page shows its state ("Kuruluyor…", "Kurulamadı, tekrar dene").
- If the first start is offline, retry on the next start.
- Credit uBOL and its GPLv3 licence in the about box. That is not required, but it is good practice.
- Never ship uBOL inside the binary.

**Cost of this choice.** The browser does not block ads until the first download finishes, about 9 MB, plus the 0.5 s `AddBrowserExtension`.

### 8. Isolation and start-up time

**Same profile: the UI is reachable (r1 and r2, webview B, `http://xbp.ui/` with Taser's CSP and an IPC handler)**
- The probe's `<all_urls>` content script was injected into the UI page (`data-xbprobe=1`).
- `chrome.scripting.executeScript({world:'MAIN'})` reached `window.ipc`, and **B's IPC handler received `probe-from-main-world-ipc` from `http://xbp.ui/`**. Taser's origin check (`is_ui_origin`) would accept it, because the message really comes from the UI origin.
- Taser's UI is `http://xb.ui/` (wry maps `xb://ui/`), so `<all_urls>` matches it.
- The CSP does not help: extension scripts are not subject to the page's CSP.
- uBO also applied cosmetic filtering to that page.

**Separate profile: clean (webview C, profile `XbUi`, same environment)**
- No injection, no IPC, no cosmetic changes.
- `GetBrowserExtensions` lists only the two built-ins.
- Building C took 108–116 ms, against 74–120 ms for B.
- The custom protocol and IPC work the same.

**Decision: UI and overlay get their own profile.** `ui::build` and `ui::build_overlay` get `.with_profile_name("XbUi")`. Content tabs stay in the default profile, which holds the user's cookies and logins today, and extensions are only ever added there. Existing users keep their sessions.

**Start-up time.** Release build, scratch `LOCALAPPDATA`/`APPDATA`, 1 warm-up plus 10 rounds, 8 s apart, the four configurations interleaved round-robin, median in ms since process creation. The toggles were a temporary env gate in `src/ui.rs`, since removed.

| Configuration | window-shown | ui-webview-created | first-tab-created | ui-ready | ui-ready vs s0 (median of per-round differences) |
| --- | --- | --- | --- | --- | --- |
| s0: v0.2 as is | 98.6 | 497.1 | 645.0 | 648.5 | |
| s1: extensions enabled | 100.5 | 577.6 | 801.3 | 804.5 | +44 |
| s2: s1, plus UI and overlay in profile `XbUi` | 127.7 | 614.6 | 820.0 | 824.4 | +99 |
| s3: s2, plus uBOL installed in the content profile | 111.3 | 519.2 | 750.8 | 754.5 | +71 |

**The machine was loaded and the numbers are noisy.**
- The s0 baseline is 648 ms here, against 362 ms in README's v0.2 row on the same build. Another session was compiling in a parallel worktree.
- Within a configuration, `ui-ready` ranged over 420–1,294 ms. The per-round differences against s0 range from −233 ms to +750 ms.
- Read the table as direction, not size:
  - Enabling extensions costs a few tens of ms.
  - A second profile for the UI adds roughly as much again, because WebView2 initializes two profiles before the first tab instead of one.
  - An installed uBOL adds nothing measurable (s3 ≤ s2). Its DNR rules are already indexed and its service worker only starts on demand.
- **Task 2 must repeat this on a quiet machine** with the real implementation before closing.

## Part B: design

### B.1 File layout

| Path | What |
| --- | --- |
| `%LOCALAPPDATA%\Taser\extensions\<id>\<version>\` | Unpacked extension (writable: WebView2 writes `_metadata\generated_indexed_rulesets` there) |
| `%LOCALAPPDATA%\Taser\extensions\<id>\<version>.tmp\` | Unpack target, renamed into place when complete. Leftovers are deleted on start. |
| `%APPDATA%\Taser\extensions.json` | Taser's record, via `store.rs` (atomic write, limits): `[{id, version, dir, source: "cws", developer_key_sha256, installed, preinstalled}]`, plus `{first_run_ubol: "pending", "done" or "user_removed"}` |
| `src/crx.rs` | CRX3 reader and verifier, and the safe unzip (being built in the crx worktree) |
| `src/net.rs` | WinHTTP GET with a size cap and timeout, off the UI thread, results sent as `UserEvent`s |
| `src/extensions.rs` | The model: list (from `GetBrowserExtensions`, built-ins filtered, merged with `extensions.json`), install, remove, enable, update check, first-run uBOL |
| `src/native/extensions.rs` | `Profile7` and `BrowserExtension` calls and their completion handlers |
| `src/cws.rs` | CWS detail URL parsing, the store-button hook script, the sentinel URL |
| `ui/js/extensions.js` | Uzantılar page (overlay) and the toolbar puzzle button |

WebView2's own profile is the source of truth for *what is installed and enabled*. `extensions.json` adds what WebView2 does not keep: version, source and the developer key for updates.

On start, after the first content webview, Taser reconciles the two once with `GetBrowserExtensions`:
- **On disk but unknown to WebView2**, e.g. a profile reset: re-add it.
- **Known to WebView2 but missing from the record:** show it as "unknown source", removable.

### B.2 Dependencies

| Crate or feature | Why | Size |
| --- | --- | --- |
| `miniz_oxide` 0.9.1 (no default features, `with-alloc`) | Inflate for the zip in a CRX | Part of the +56,320 B measured for `src/crx.rs` |
| `windows` feature `Win32_Security_Cryptography` | CNG: SHA-256, RSA PKCS#1 v1.5, ECDSA P-256 | Same |
| `windows` feature `Win32_Networking_WinHttp` | Downloads and update checks | ≤ +15,872 B (stand-alone upper bound) |

No zip, sha2, rsa, ring, prost, reqwest or tokio. Protobuf (a few varints) and the zip central directory are read by hand in `crx.rs`.

**Expected binary:** 1,260,032 + ~56 KB + ~16 KB + the feature code, about 1.4 MB.

### B.3 Security model

1. **Profiles.** UI and overlay run in profile `XbUi`, where extensions are never added; the selftest asserts `GetBrowserExtensions(XbUi)` holds only the two built-ins. Content tabs and extension pages run in the default profile.
2. **The UI IPC stays the only bridge.** Content tabs keep `IsWebMessageEnabled=false` and no host objects. The store hook (B.4) uses a cancelled navigation, not a bridge.
3. **Only store packages.** `Policy::WebStore`: the CWS publisher proof (`kPublisherKeyHash`) and the developer proof must both verify, and `crx_id` must equal SHA-256(developer key)[0..16] and the requested id. Updates must keep the same developer key.
4. **The package is untrusted until verified.** Size caps on the download (e.g. 64 MB), the unpack (e.g. 256 MB, 10,000 entries) and the manifest (1 MB, JSON). Safe unpacking as in A.5. Nothing is ever executed by Taser.
5. **The user decides.** Every install shows Taser's own confirmation in the overlay: name, version, a Turkish rendering of the permissions and host access, "Ekle" or "İptal". The first-run uBOL install is the one exception, because the user asked for it as part of the product.
6. **Extension pages.** `chrome-extension://<id>/…` is allowed in content tabs only for installed, enabled ids, and never typed as an external scheme. The address bar shows the extension's name.
7. **Tabs that extensions open.** `chrome.tabs.create` arrives as user-initiated `NewWindowRequested`. It opens a background tab like any other new window, under the same policy.

### B.4 CWS install flow (task 4)

**Detect**
- On `SourceChanged`/`HistoryChanged`, since the store is a single-page app, match `^https://chromewebstore\.google\.com/detail/(?:[^/?#]+/)?([a-p]{32})(?:[/?#]|$)` (`cws::detail_id`). The slug excludes `?` and `#`, so an id in a query string or fragment never counts as the page's id.
- The toolbar shows **"Ekle"**, or "Kaldır" when the id is installed, or a spinner during an install.

**Store button**
- An initialization script (`cws::HOOK_SCRIPT`) on all content tabs. It does nothing unless `location.origin === 'https://chromewebstore.google.com'`.
- It wraps `chrome.webstorePrivate.beginInstallWithManifest3` (install) and `chrome.management.uninstall` (remove, r7) so that:
  - in the top frame only, it navigates the tab to the sentinel `https://chromewebstore.google.com/_xb/install/<id>` (or `/_xb/remove/<id>`); in a subframe it only refuses
  - it returns `'user_cancelled'`
- The content `NavigationStarting` handler (`attach_policy`) calls `cws::sentinel_decision(source, uri, IsRedirected)` for every navigation:
  - `Pass` for anything not under `/_xb`;
  - `Cancel` for every navigation under `/_xb`, and nothing more, unless the next rule holds;
  - `Ask(action, id)` (cancel, then open the confirmation) only when the navigation is not a redirect hop, the tab's current `Source` is a CWS detail page, and the sentinel's id equals that page's id.
- Both install and remove go through Taser's confirmation, so even a script on the store page itself can only open a dialog the user must accept. A third-party page can at most cause nothing.

**Install**
1. WinHTTP download of `cws::crx_url` into memory (`net::get`: size-capped, `https` only on every hop, no IP-address or single-label hosts, at most `net::MAX_REDIRECTS` redirects followed by hand). The CRX signature, not the host, is what makes the package trusted. `prodversion` is the WebView2 runtime version, checked with `cws::is_version`, with a fixed fallback.
2. `crx::verify` with `Policy::WebStore`.
3. Confirm (B.3.5) with the name and version from the verified manifest (resolve `__MSG_…__` names from `_locales`) and `cws::describe_permissions`. Nothing is written to disk before the user accepts.
4. Safe unpack to the `.tmp` folder, then insert `"key"`, then rename.
5. Call `AddBrowserExtension`. Check that the returned `Id` equals the requested id; if not, remove it and fail.
6. Record it in `extensions.json`.
7. Reload the store page, so it shows "Remove from Chrome".

**Remove** from the store button: confirm ("Kaldır" or "İptal"), then the task 5 removal path.

**Update checks** (`cws::update_check_url`, `cws::parse_update_response`): batch about 100 ids per request and pass `cws::MAX_UPDATE_RESPONSE` as the body cap. An entry without a `hash_sha256` is dropped. The caller checks the downloaded file's SHA-256 against it, that the version is newer than the installed one, and that it equals the version in the CRX manifest.

Errors are shown in Turkish in the overlay. Partial folders are removed.

**First-run uBOL.** The same steps without the confirmation, with id `ddkjiahejlhfcafbddmgiahcphecmpfh`. It is queued after `ui-ready` so it does not touch start-up time.

### B.5 Management UI (task 5)

**Menu: "Uzantılar"** opens an overlay page listing each extension:
- icon, read by Rust from the folder, PNG only, ≤ 32 KiB, sent as a `data:` URL
- name and version
- an enable switch: `Enable(bool)`
- "Seçenekler": opens `options_page` or `options_ui.page` in a new tab
- "Kaldır": `Remove`, then delete the folder and the record. Ask first, and say the extension's settings are deleted too (`Remove` wipes its storage, u4).
- "Güncellemeleri denetle"

**Toolbar: a puzzle button**, shown when at least one enabled extension has an `action`. It lists those extensions. Picking one opens the **popup surface**:
- a fourth child webview in the **default** profile, 360x480 under the button, built on demand
- carrying the `tabs.query` shim from A.3, with the active tab's URL
- closed on Esc, on a click outside, on a tab switch, or when the popup calls `window.close()`

The overlay cannot host it, because the overlay is in the UI profile.

### B.7 Risks

- **Undocumented store behaviour.** `chrome.webstorePrivate` and its call shape are the store's private contract with the browser, and Google can change them. The toolbar "Ekle" button depends only on the URL, so it keeps working if the hook breaks.
- **MV2 withdrawal.** This does not affect uBOL. Any MV2 extension a user installs may stop working on a future runtime.
- **The popup shim is a heuristic.** It matches the active tab by URL; two tabs on the same URL may confuse an extension's per-tab view. Extensions that use `tabs.getCurrent`, `windows.getCurrent` or `lastFocusedWindow` are not covered.
- **Edge-branded native dialogs.** If the hook misses an API, the store can still open "…to Microsoft Edge?" dialogs. Accepting one would install outside Taser's record; the reconcile step shows such extensions as "unknown source".
- **Start-up time.** Extensions plus a second profile cost an estimated 40–100 ms before the first tab (section 8). If that proves too much, the content tab could be created before the UI webview finishes, so both profiles initialize in parallel. Not tried in the spike.
- **Disk use:** about 47 MB for uBOL once WebView2 has indexed its rulesets.
- **Users can install anything from the CWS**, including malicious extensions. The permission dialog is the only gate, as in Chrome.
- **Runtime updates** may change any of the above. Re-run the probe on each new major runtime.

## Not verified

- Accepting WebView2's native "Add … to Microsoft Edge?" dialog: whether it installs, where, and whether Taser would see it. That needs a desktop click, which the spike's rules forbid.
- Cosmetic filtering by uBOL on a real ad site, and uBOL's per-site mode switch from the popup changing behaviour.
- `chrome.action.openPopup`, `chrome.tabs.getCurrent` and `lastFocusedWindow` from popups in a separate webview.
- Start-up cost below about 50 ms of precision. The timing machine was loaded (section 8).
- uBOL behaviour on runtimes other than 157.0.4341.46.
- Scale other than 1.0 for the popup surface.
