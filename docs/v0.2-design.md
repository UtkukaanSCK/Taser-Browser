## Part B: design

### 1. Popup surface: a third child webview (the overlay)

**Decision.** Add one extra child webview of the tao window, `overlay`, used for every popup: address suggestions, the main menu, the bookmark editor, the downloads panel and settings.

- It loads `xb://ui/overlay.html` through the same `serve()`, so it gets the same CSP.
- It sits on the same origin, `http://xb.ui/`, so it uses the same IPC handler with the same `is_ui_origin` check and the same navigation and new-window deny rules.
- `browser_accelerator_keys`, `default_context_menus` and devtools are all off, exactly as for the UI webview.
- At most one popup is visible at a time.

The strip also needs its own background once the page is transparent. | lines 205–213; `screen-p36-e1-transparent-ui.png` |
| E2 | Third opaque child webview (360x240 at 150,30) | Build took 45 ms (26.7 / 29.9 / 33.9 ms in later runs), and the first script result came 25–31 ms after that. **Rules that follow from the experiments**

- **Bounds.** Size the overlay to the visible popup rectangle exactly. Draw no shadow outside it. Use square corners, or corners of 6 px or less (with `with_transparent`, the corner pixels are tiny dead zones).
- **Window edges.** The overlay is a child, so it cannot extend past the window's client area. Flip or clamp menus at the window edges, and scroll long lists.
- **Z-order.** Raise the overlay (`native::raise`) on every show. Close it on tab switch, so a newly shown content view never ends up above it.
- **Focus.** Popups that own the keyboard (menu, editor, settings) call `overlay.focus()`. The suggestions list must *not* take focus: the address `<input>` keeps it, and the UI forwards ↑/↓/Enter/Esc to Rust, which re-renders the overlay.
- **Dismiss.** The overlay closes on any of the following:
  - Esc pressed inside the overlay
  - focus moving to the content or UI webview (`Controller.add_GotFocus` on both; clicking a page moves focus to it)
  - `WindowEvent::Focused(false)`, `Resized`, `Moved` or `ScaleFactorChanged`
  - a tab switch or a navigation
  - the UI process failing
- **Startup.** The overlay is created lazily, on first use (about 30–45 ms plus about 30 ms to first paint), then hidden and reused. It stays off the startup path, so the 500 ms budget is untouched.
- **DPI.** Bounds use logical pixels (wry `Rect`). Only scale 1.0 was measured; per-monitor DPI change is **not verified**, so the overlay just closes on `ScaleFactorChanged`.
- **Rejected alternatives**
  - Enlarging the UI webview (E1): content clicks are blocked.
  - Native popup windows (owned `WS_POPUP` or `TrackPopupMenu`): more native code, extra activation and focus handling, and no shared styling. Keep `TrackPopupMenu` only as a fallback for a plain menu.

### 2. Persistent data

**Location and files.** Everything lives in `%LOCALAPPDATA%\X-Browser\`, next to `EBWebView\`, in UTF-8 JSON.

| File | Content | Size limit (read) | Item caps | Written |
| --- | --- | --- | --- | --- |
| `settings.json` | `{"v":1, …}` flat key/values | 64 KiB | — | on change |
| `window.json` | rect (logical), maximized, monitor hint | 4 KiB | — | debounced 2 s, plus at exit |
| `session.json` | tabs `[{url,title}]`, active index | 1 MiB | 500 tabs | debounced 2 s, plus at exit |
| `bookmarks.json` | `[{url,title,added}]` | 4 MiB | 10,000 | on change |
| `history.jsonl` | one `{"u","t","ts"}` object per line, append-only | 16 MiB | 50,000; compact to 40,000 at startup | buffered, flushed every 2 s and at exit |

**Content rules.**
- Store only `http`/`https` URLs (`url::is_web_url`), each at most 8 KiB (`MAX_NAV_INPUT`).
- Cap titles at 512 chars.
- Files are untrusted on read: apply the same checks again on load and drop entries that fail them.

**Atomic write.** Write `<name>.tmp` in the same directory, call `sync_all`, then `std::fs::rename` over the target. On Windows that is `MoveFileExW(MOVEFILE_REPLACE_EXISTING)` on the same volume. The first successful save of each run first copies the previous good file to `<name>.bak`. `history.jsonl` appends whole lines; a torn last line is ignored on read.

**Corruption.** Parse failure, a file over its size limit, or invalid UTF-8 all lead to the same steps:
1. Rename the file to `<name>.corrupt`, replacing any older one.
2. Load `<name>.bak` if it parses; otherwise use defaults.
3. Log it with `eprintln!`. Never panic, never block startup.

For `history.jsonl`, bad lines are skipped one by one.

**Versioning.** Every object file carries `"v":1`. Unknown fields are ignored and missing fields default (`#[serde(default)]`). A file with a higher `v` is read where possible but never rewritten, so a downgrade cannot destroy newer data.

**Single writer.** Only one process ever writes, which section 3 guarantees.

**serde_json versus hand-written code.** Measured on the release profile (LTO, strip) with a prototype store:

| Variant | exe bytes | Delta vs baseline |
| --- | --- | --- |
| Baseline (`33b478e`) | 684,544 | — |
| `serde` + `serde_json 1.0.154` | 787,968 | **+103,424 (+15.1 %)** |
| Hand-written JSON, f64 numbers | 727,552 | +43,008 |
| Hand-written JSON, integers only | 710,144 | +25,600 |

**Decision:** `serde` (with `derive`) and `serde_json` 1.x.

**Crate justification.**
- It is the standard, heavily fuzzed JSON implementation. Escapes, surrogate pairs, numbers and depth limits are already right, and those are exactly the untrusted-input cases a hand parser gets wrong.
- `derive` replaces per-type mapping code in five files across four tasks.
- The same serializer builds the JSON that Rust pushes into the UI (`xb.render(...)`), which removes hand-built JS string escaping.
- The binary stays at about 0.79 MB, 8 % of the 10 MB budget.
- Cost: about 100 KB, plus some compile time for `serde_derive`. No other new crate.

### 3. Single instance (task 4)

**Detection.** The first thing `main` does, before creating any window or WebView2 environment, is call `CreateMutexW(None, true, "Local\X-Browser-<hash of the data dir path>")`.
- Deriving the name from the data dir keeps a scratch-`LOCALAPPDATA` selftest independent of the user's instance.
- If the mutex already exists (`ERROR_ALREADY_EXISTS`), this is the second instance.

**Hand-off.** The first instance creates a message-only window (`HWND_MESSAGE`) with class `XBrowserIpc-<hash>`. The second instance then:
1. Finds that window with `FindWindowExW(HWND_MESSAGE, …)`.
2. Calls `AllowSetForegroundWindow(owner pid)`.
3. Sends `WM_COPYDATA` with `dwData = 1`, carrying the UTF-16 command-line URL, or an empty payload meaning "just activate". It uses `SendMessageTimeoutW` with a 2 s timeout and `SMTO_ABORTIFHUNG`.
4. Exits. It never touches the profile, so it causes no ProfileBusy error.

If the hand-off fails, because the first instance is hung or shutting down, the second instance shows the existing "already running" style dialog and exits.

**Untrusted input.** Any same-desktop process can send `WM_COPYDATA`, so the first instance treats the payload as untrusted:
- It accepts only `dwData == 1` and `cbData ≤ 16 KiB` that is even and valid UTF-16, with no NULs.
- It decodes the URL, then runs `url::resolve_input`. Only `Resolved::Url` that passes `is_web_url` (http/https, never `xb.ui`) is accepted.
- An accepted URL is opened as a new active tab, and the window is restored and activated.
- Everything else (`file:`, `javascript:`, search text, blocked results) is dropped silently, beyond activating the window.

The same function serves the first instance's own `argv[1]` (today in `main.rs`). The message is handled on the UI thread through a `UserEvent::OpenFromOtherInstance(String)`.

New `windows` features: `Win32_System_DataExchange` (for `COPYDATASTRUCT`). No new crate.
